# Agent Forge Implementation Plan

Status: draft for review

This document is an implementation plan, not authorization to start implementation. It records the design to approve before replacing the current schema and source layout.

## 1. Decisions

- Agent Forge is a metadata integration service. It does not inspect, execute, scan, certify, or otherwise verify upstream content.
- No field guarantees safety, trustworthiness, accuracy, completeness, freshness, compatibility, or availability.
- The four base types are mcp, plugin, skill, and general.
- general replaces the current other source/category name. It is for Agent tools outside the other three base types and requires `toolType` and `agentUse`.
- bundle is a fifth published type. It composes packages and is not an upstream tool category.
- In the first GitHub-native phase, canonical JSON/YAML files in Git are the only writable source of truth; a canonical database is a later phase.
- GitHub Pages is a presentation and submission entry point. Pull Requests modify canonical files; Agent files, JSON indexes, and manifests are generated by Actions.
- Bundle overrides are local to one Bundle and never rewrite a source package compatibility range.
- Public static files remain a supported read-only contract.

### Schema v2 naming and two-layer mirror model

- Schema v2 does not use `kind`, `memberKind`, or `versionKind`.
- The package category uses `type`; Bundle members use `memberType`; version comparison metadata uses `versionScheme`.
- A General tool's specific nature uses `toolType`, avoiding the confusing `typeRef.type` combination.
- Installable candidates for a package use `distributions[]`. `distributions[].type` identifies `git`, `release`, `archive`, or `registry`; it is not an Agent Forge catalog source.
- Agent Forge catalog mirrors are described separately by source manifest/index fields such as `mirrorOf`, `sourceMirrors`, `revision`, and `priority`. A catalog mirror copies metadata, not necessarily the plugin artifact.
- A package may list multiple distributions. The installer chooses among them based on network, region, format, and local policy. Agent Forge only integrates the candidates; it does not download, proxy, compare, or guarantee them.
- When multiple catalog sources return the same package ID, version, and revision, consumers may switch mirrors. If revisions differ, clients must report a conflict or apply an explicit priority rather than silently merging records.

## 2. Scope and non-goals

### In scope

- Web UI and API for creating, editing, searching, reviewing, and publishing metadata.
- Agent registration and Agent-version compatibility declarations.
- Types mcp, plugin, skill, general, and bundle.
- Controlled facets for capabilities, effects, data practices, permissions, runtime, and integrations.
- Optional per-Agent, per-type read-only database snapshots; they are not required for first-release online search.
- Static JSON projections.
- Bundle range intersection, member locking, and Bundle-local overrides.
- Audit history, generated release revisions, checksums, generated-file signatures, and rollback.

### Explicitly out of scope

- Malware scanning or source-code review.
- Verifying publisher claims, URLs, checksums, signatures, registry entries, or compatibility claims.
- Executing installation commands or upstream scripts.
- Calling a facet a security certification.
- Maintaining binary artifacts or acting as a package mirror.
- Direct manual edits to generated Agent source files.

## 3. Architecture

    Web UI / API
         |
         v
    Canonical database <--- audit log and outbox events
         |
         v
    Projection and release worker
         |
         +--> online search API
         +--> Agent x type SQLite databases
         +--> static JSON indexes and package records
         +--> release manifest and checksums

Recommended sibling layout:

    sourcerepo/
    |- agent-forge/              # Public schemas and generated read-only data
    '- agent-forge-platform/     # Web, API, database, worker, deployment

The platform may write a generated branch or release directory, but generated files are never the primary maintenance workflow.

### First-phase GitHub-native workflow

The first phase does not require a server, PostgreSQL, FastAPI, or a long-running Worker:

    GitHub Pages UI / Issue Forms
             |
             v
    Pull Request and GitHub permissions
             |
             v
    GitHub Actions validation and generated preview
             |
             v
    Merge Queue -> main -> Pages / Releases

Pages cannot safely host a dynamic API, OAuth callback, PostgreSQL, or write token. Issue Forms collect submissions, Actions create or validate Pull Requests, required checks and reviews gate the Merge Queue, and Git history plus PRs plus Checks provide the audit trail. The backend database/API/Worker moves to a later phase.

Actions must not rely on a normal `GITHUB_TOKEN` created by an Issue Form workflow to trigger subsequent validation workflows, because GitHub suppresses recursive workflow triggers from that token. Use a least-privilege GitHub App token or a `workflow_run` orchestration. Merge Queue workflows must listen for `merge_group` and use the same required Checks in branch protection.

### Development deployment

After implementation, the first integration deployment targets the owner's local server `metaone@192.168.100.197`. This is a development and test environment, not the final production architecture.

The deployment must use a separate service user, application directory, virtual environment, data directory, systemd services for API and Worker, and a reverse proxy for the test HTTPS endpoint. Database connections, OAuth credentials, GitHub App credentials, and session secrets are environment variables and never committed. GitHub Pages serves only static UI and public JSON; it cannot host the API, OAuth callback, PostgreSQL, or Worker.

GitHub OAuth requires an explicit callback URL. If a private LAN address cannot satisfy GitHub's HTTPS callback requirements, development must use a dedicated OAuth App and an HTTPS tunnel; production credentials must never be embedded in source code.

## 5. Canonical data model

In the first GitHub-native phase, these entities are represented by canonical JSON/YAML files changed through Pull Requests. The relational table mapping is reserved for the later backend phase; field semantics remain the same for migration.

### agents and types

Stable identity, display information, version scheme, lifecycle, descriptions, and deprecation state.

### packages

Common package identity and descriptive metadata:

    id, slug, displayName, description, license
    homepage, repository, documentation, keywords
    status, createdAt, updatedAt

The package ID does not change when the package is projected to multiple Agents.

### package_versions

    id, packageId, version, versionScheme
    releaseNotes, checksumClaims, signatureClaims, publishedAt

Checksums and signatures are recorded claims or supplied material. This project does not verify them.

### package_targets

    id, packageVersionId, agentId, typeId
    agentVersionRange, targetMetadata, installMetadata, status

One package version can target pi/plugin and hermes/plugin with different ranges and target metadata.

### bundles and bundle_members

A Bundle has its own identity and lifecycle. A member stores:

    bundleId, packageVersionId, required
    declaredRangeSnapshot
    overrideRange, overrideReason
    overrideActor, overrideCreatedAt

The declared range is snapshotted so later package edits cannot silently rewrite an existing Bundle.

### bundle_targets

    bundleId, agentId, effectiveRange
    rangeSource, conflictStatus, calculationRevision

### facets and relations

Use a controlled vocabulary plus normalized relations:

    facets
    package_facets
    package_effects
    package_data_practices
    package_permissions
    package_integrations

Each declaration retains source, optional evidence reference, and declaration timestamp. Evidence is stored, not checked.

### releases, projections, sync_jobs, audit_events

Track generated revisions, file hashes, sync status, retries, failures, actor actions, and rollback points.

## 7. Bundle rules

For each Agent:

    effective(member) = overrideRange if present, otherwise declaredRange
    bundleRange(agent) = intersection of all required member effective ranges

Rules:

1. An empty intersection blocks publication for that Agent.
2. An override is stored only on the Bundle member.
3. An override requires a reason and actor.
4. A widening override shows an explicit warning before publication.
5. Optional members are conditional and do not silently narrow the required intersection.
6. Cyclic Bundle references are rejected.
7. Bundle publication locks member versions and checksum claims.
8. Bundle facets are derived from member facets. Required-member effects and data practices are unioned; optional-member facets are conditional.
9. A Bundle cannot hide a member's permissions or data practices.

## 8. Local search databases

Generate one database per Agent and type:

    agents/<agent>/releases/<release>/mcp.db.zst
    agents/<agent>/releases/<release>/plugin.db.zst
    agents/<agent>/releases/<release>/skill.db.zst
    agents/<agent>/releases/<release>/general.db.zst
    agents/<agent>/releases/<release>/bundle.db.zst

The current four base types plus bundle therefore produce five databases per Agent.

Each optional database snapshot contains compact metadata, target compatibility, facets, an FTS5 index, and URLs/checksum claims. It does not contain binary artifacts. Online Pages JSON search does not depend on a snapshot being present.

current.json pins all database files to one release revision. Clients stage changed files, verify hashes, and atomically switch the local release only after required databases are complete.

The first online search path uses the API and static JSON and does not require a snapshot. If snapshots are generated, use complete compressed snapshots first; add incremental updates only after measurement demonstrates a need.

Local operations should support:

    search --agent pi --type plugin gui.modify
    search --agent pi --capability filesystem.write
    search --agent pi --data financial --action transmit
    info <package>
    sync --agent pi --types plugin,bundle

## 10. Synchronization workflow

First-phase GitHub-native workflow:

1. Submit canonical package JSON/YAML through an Issue Form or Pull Request.
2. Actions validate shape, type fields, range syntax, facet/subtype IDs, and references.
3. Actions calculate affected Agents/types, Bundle Agent intersections, and facet unions.
4. Actions check the ten-minute cutoff, duplicates, nested cycles, and generated paths.
5. Failed checks comment on the PR and block Merge Queue.
6. Required Checks, reviews, and Merge Queue merge into `main`.
7. Pages builds static JSON and the web UI.
8. Scheduled Actions at UTC `00:00`, `08:00`, and `16:00` generate optional SQLite snapshots, hashes, and release metadata.
9. After all projections validate, create one immutable timestamped Release.
10. Update the latest Pages manifest last; on failure preserve the previous stable Pages and Release.

The later backend workflow may add a canonical database, outbox, long-running Worker, and dynamic API, but it must reuse the same schema and projection checks.

The public manifest must never point to an unvalidated mixture of revisions.

Each Agent Dashboard includes type/package/version counts, subtype distribution, type growth over releases, facet rankings, unknown compatibility count, Bundle/member/nesting counts, recently updated packages, and links to type searches.

## 14. Acceptance criteria

- A package is created once and projected to multiple Agents without duplicated canonical records.
- An edit produces a predictable affected projection set.
- A failed target projection cannot publish a partial release.
- Bundle ranges are reproducible from locked members and overrides.
- Bundle overrides do not modify source package declarations.
- Facets are searchable locally and through the API.
- Facets and compatibility data are visibly presented as unverified metadata claims.
- Online API and Pages search work without SQLite; optional snapshots support offline search when generated.
- A client can atomically update between release revisions.
- Generated JSON and SQLite outputs validate against the same revision.
- Every write and publication has an audit event.
- Rollback restores a generated release without rewriting canonical history.
- Tests cover unknown types, invalid facets, invalid ranges, empty intersections, cycles, partial sync failures, and idempotent retries.

## 15. Risks to review

- Per-Agent projections duplicate compatible metadata in generated artifacts. This simplifies offline clients but requires storage and generation measurements.
- Per-type databases reduce update size but require release coordination for Bundle references.
- SQLite needs a stable reader contract and migration policy.
- A controlled vocabulary requires ownership, aliases, deprecation rules, and backward compatibility.
- Publisher-declared data practices can be incomplete or wrong; the UI must never present them as verified security facts.
- Unsupported compatibility syntax must fail closed for automatic publication.
- Full snapshots are simplest initially; delta updates should only be added after measurement.

## 16. Latest Confirmed Decisions

- The first priority Agent is `dsh` (DeepSeek Harness). Other Agents are added as reliable public metadata becomes available; Agent Forge integrates those claims and does not verify them.
- The repository is `metaone01/agent-forge`, default branch `main`, and remains private during development.
- GitHub Actions publishes at UTC `00:00`, `08:00`, and `16:00`. A release uses one shared UTC timestamp, for example `dsh-plugin-20260930T160000Z.db.zst`. SQLite assets are optional; Pages JSON and the online API do not require them.
- Package, version, target, Bundle, and public custom-facet records become public no earlier than ten minutes after successful submission. The delay is an abuse-control window, not verification.
- Initial rate limits are ten package submissions per identity per minute and one hundred per ten minutes. Exceeding a limit blocks new publication jobs, requires a fresh confirmation or CAPTCHA, and allows administrator release. Re-authentication is not sufficient proof by itself.
- GitHub repository permissions are rechecked before every write and high-risk operation. If the permission API fails, the operation is rejected; stale permission cache must not authorize the operation.
- When a user loses repository access, their existing records remain. Further edits are blocked. Other authorized maintainers can revert through a new audited revision; history is never rewritten.
- All five types have an optional administrator-controlled subtype next to the type. A package selects at most one subtype at creation; the same value is copied to every Agent/type projection. Users cannot create or override subtypes.
- User facets take effect immediately but are stored under a separate `customFacets` property and never masquerade as core facets.
- All types share dependency and conflict relations. Bundle is a specialized type, permits nested Bundles, has members without required/optional distinction, derives its facets as the union of all members, and has an Agent set equal to the intersection of member Agent sets. Agent Forge only exposes metadata; installers choose how to install for an Agent.
- Unknown Agent compatibility is represented explicitly as `agentVersionRange: null`, `compatibilityStatus: unknown`, and an optional note. It can be listed but cannot participate in automatic compatibility filtering or Bundle range calculation without a Bundle-local override.

## 18. Deliberate corrections to the original proposal

- SQLite distribution is not a first-release requirement. It is an optional cache/snapshot layer for offline or high-frequency consumers.
- Removing a user's records after repository access is lost would break references and history. Retention plus revoked edit access and audited forward reverts is safer.
- Requiring OAuth login again is not an adequate anti-abuse control. A compromised account can re-authenticate; rate limits, cooldowns, CAPTCHA, audit signals, and administrator review are also required.
- A Bundle member cannot be represented only by `packageVersionId` because a version can have multiple Agent targets. The member must identify the target or nested Bundle explicitly.

## 19. Final operating rules for the first implementation

- GitHub Actions publishes only at UTC `00:00`, `08:00`, and `16:00` (`0 0,8,16 * * *`). A record is eligible only when it passed validation at least ten minutes before the publication point; later records wait for the next point. This preserves the ten-minute public-delay rule.
- Package, version, target, Bundle, and public custom-facet submissions are rate-limited at ten package submissions per identity per minute and one hundred per ten minutes. The limit blocks new publication jobs, requires fresh confirmation or CAPTCHA, and permits administrator release. Re-authentication alone is insufficient.
- Custom facets take effect immediately after format validation, but remain in a separate `customFacets` property and are always labelled user-defined and unverified. A package projection still follows the ten-minute public delay.
- The package record has one administrator-selected optional subtype adjacent to its type. The same subtype is copied to every Agent projection; users cannot create or override subtypes.
- All types share dependency/conflict relations. Bundle is specialized, permits nested Bundles, has members without required/optional distinction, derives all facets as the union of all members, and exposes only the intersection of member Agent sets. Agent Forge provides metadata only; installers choose installation behavior.
- Bundle members use `memberType: package|bundle` and `memberId`, not only `packageVersionId`. Cycles are rejected.
- Unknown Agent compatibility uses `agentVersionRange: null`, `compatibilityStatus: unknown`, and an optional note. Unknown values may be listed but do not participate in automatic compatibility filtering or Bundle calculation unless a Bundle-local override is supplied.
- Repository permissions are rechecked before every write and high-risk operation. A permission API failure rejects the operation; stale cached permissions never authorize it. Existing records remain after a user loses access, while further edits are blocked and audited forward reverts remain possible.

## 20. GitHub-native first release

- Pages provides browsing, lightweight JSON indexes, package details, and a link to a prefilled Issue Form. A contributor with repository write access may also open a Pull Request directly.
- Issue Form submissions are converted into proposal branches and Pull Requests by Actions. No Pages JavaScript stores or exposes a GitHub write token.
- Pull Request Actions validate schema, cross-file identity, duplicate records, subtype vocabulary, facets, Bundle Agent intersections, nested cycles, and the ten-minute cutoff. They do not inspect or verify upstream links.
- Required Checks, review rules, and Merge Queue gate merges into `main`.
- After merge, Pages is built from generated JSON. Scheduled Actions run only at UTC `00:00`, `08:00`, and `16:00`; eligible records must have passed validation at least ten minutes before the point.
- The release workflow generates all projections, validates them, creates one timestamped Release, uploads optional database snapshots, deploys Pages, and updates the latest manifest only after assets exist.
- The first phase provides no dynamic API, server-side transaction, or secure custom OAuth callback. Those belong to the later backend phase.

3. GitHub Pages serves the UI, Dashboard, static search JSON, package details, and Issue Form entry point.
4. GitHub Actions perform schema/semantic validation, previews, Pages generation, and Release assets.
5. Merge Queue and branch protection gate merges.
6. SQLite is an optional snapshot, not a first-phase online-search dependency.
7. Backend database/API/Worker work is later and must reuse the same schema and projection rules.

### Public types and fields

- Types are `mcp`, `plugin`, `skill`, `general`, and `bundle`.
- `general` replaces `other` and requires `toolType` and `agentUse`; it does not use `typeRef.type`.
- Every type has one optional administrator-controlled `subtype`; users cannot create or override it.
- A package selects at most one subtype, copied to every Agent/type projection.
- Skin is `plugin` with `subtype=skin`, not a new first-class type.
- README and LICENSE are links (`links.readme`, `links.license`), not copied or reviewed content.
- User facets take effect immediately under separate `customFacets`; they cannot override core facets and are labelled user-defined and unverified.
- Unknown Agent compatibility uses `agentVersionRange: null` and `compatibilityStatus: unknown`; it may be displayed but cannot participate in automatic compatibility filtering or Bundle calculation.

### Bundle rules

- Bundles may be nested.
- Members have no required/optional distinction.
- Members use `memberType=package|bundle` and `memberId`, not only `packageVersionId`.
- Catalog mirrors and plugin distributions remain separate: the former belongs to source manifests/indexes, the latter to package versions or targets.
- Bundle Agent set is the intersection of all member Agent sets.
- Bundle capabilities, effects, data practices, permissions, runtime, and integrations are the union of all member facets.
- Cycles are rejected.
- All types share dependency/conflict relations; Bundle is specialized.
- Agent Forge exposes metadata only; installers choose installation behavior.

### Submission and release rules

- Pages links to a GitHub Issue Form; maintainers may also open PRs directly.
- Actions validate schema, duplicate identity, facets, subtypes, Bundle intersection, nested cycles, and generated paths.
- Issue Form PR creation must use a restricted GitHub App token or `workflow_run`, not a normal `GITHUB_TOKEN` that suppresses recursive workflows.
- Merge Queue workflows listen for `merge_group`.
- Package, version, target, and Bundle public projection has a minimum ten-minute delay.
- Actions publish only at UTC `00:00`, `08:00`, and `16:00` (`0 0,8,16 * * *`).
- Records must pass validation at least ten minutes before a point or wait for the next point.
- No-change points do not create empty Releases.
- Release assets use one UTC timestamp, such as `dsh-plugin-20260930T160000Z.db.zst`, and old assets are never overwritten.
- Generate and validate all projections and Release assets before updating the Pages latest manifest.

### Permissions and abuse controls

- First-phase identity uses GitHub account, PR author, reviews, and repository permissions; Pages never stores a write token.
- Recheck repository permissions before every write and high-risk operation. Permission API failure rejects the operation; stale cache never authorizes it.
- Existing records remain when a user loses access; future edits are blocked; authorized maintainers can create audited forward reverts without rewriting history.
- Initial rate limits are ten package submissions per minute and one hundred per ten minutes; excess enters cooldown and fresh confirmation/CAPTCHA with administrator release.
- Re-authentication alone is not sufficient abuse proof.

### Dashboard requirements

- Generate `data/dashboard.json` and `data/agents/<agent>/dashboard.json`.
- Show type, subtype, facet, compatibility, Bundle, lifecycle, and update statistics.
- Provide table/text alternatives, responsive layout, and keyboard access.
- Never show safety or trust scores or imply source verification.
- Dashboard, search indexes, and Releases share one data timestamp; failed statistics generation blocks Pages publication.
