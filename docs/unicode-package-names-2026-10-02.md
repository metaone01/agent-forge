# 中文包名与身份保存

此前社区采集使用只接受 ASCII 的 slug 生成规则，把中文等字符替换成 `-`，并且会截断长名称。此次审计发现 3 个现有 Plugin 的中文目录名受到影响。它们的 `id` 是稳定哈希，损失发生在 `name` 字段。

本轮直接恢复这 3 个 `name` 和 index 包名键的中文原文。已有包 ID、发行候选 ID、版本和规范记录文件位置保持不变；没有新增名称别名或运行时转换层。原文依据是保存的 GitHub 仓库地址及安装子路径，详见[恢复记录](research/2026-10-02-import/restored-package-names.json)。

## 后续规则

- `name` 保存原始 Unicode 包名，不进行连字符替换或静默截断。超过 schema 长度限制或包含控制字符的记录明确拒收。
- 已有 `id` 保持稳定；后续版本继续沿用该 ID。
- 新采集包的 `id` 来自可逆编码的上游身份，采用 UTF-8 百分号编码。例如原始身份 `author/project/中文` 对应 `plugin.author/project/%E4%B8%AD%E6%96%87`。
- 百分号编码按 UTF-8 字节使用 `%XX`，不是把一个汉字直接写为 `%xxxx`。上游字面名称 `%E4%B8%AD` 的百分号会再次编码为 `%25`，不会与“中”混为同一身份。
- Schema 同时允许直接中文 ID，例如 `plugin.中文助手`。JSON 的 `\uXXXX` 只是同一字符串的序列化方式：`"中文"` 与 `"\u4e2d\u6587"` 解码后完全相同。依赖引用须使用记录实际存储的 ID，不自行解码后重新拼接。
- 生成文件名使用 UTF-8 字节的 `~XX` 转义和完整名称的哈希后缀。例如 `/` 对应 `~2F`，“中文”对应 `~E4~B8~AD~E6~96~87`。长文件名前缀可以缩短，但完整包名和 ID 仍保存在 JSON/index 中，哈希后缀区分长名称和大小写。

普通 HTTP 服务会把请求路径中的 `%XX` 解码一次。如果实际文件名也直接包含 `%XX`，就可能发生找不到文件的问题；`~XX` 文件名避开这一次解码。它只用于生成文件路径，页面和消费者读取的 `name` 仍是原文。

## 验证与复算

回归覆盖中文名、Unicode/百分号 ID、字面百分号的身份区分、旧 ID 延续、索引更新、中断恢复，以及从真实本地 HTTP 服务读取中文包详情。所有旧来源类型的消费者需适配新增具体类型；这与保存中文原文是两个独立契约变化。

2026-10-02 本地验证：44 项回归测试全部通过；全量规范数据校验通过，保留 3,425 条既有警告（3,423 条历史版本未单独列入最新索引，2 条来源证据元数据超过建议大小）。重新生成的目录包含 57,435 个包和 60,858 条版本记录，生成过程无警告。

生成目录的 6 个来源清单与索引通过 Schema 校验。57,475 个源内索引条目（同一包可面向多个 Agent）全部核对了详情路径、包 ID、最新版本、SHA-256、revision 和来源名称；3 个恢复名称均存在于索引及检索文本中。

```sh
uv run tools/restore_package_names.py
uv run tools/restore_package_names.py --apply
uv run python -m unittest discover -s tests -v
uv run tools/validate.py --all
```
